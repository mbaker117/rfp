# RFP Matching System — Design Spec

**Date:** 2026-07-25
**Status:** Approved

---

## 1. Problem Statement

Users upload RFP/BOQ documents listing required products. The system matches each requirement against a catalog of products from registered suppliers, using deterministic code — not LLM judgment — to produce scored, explainable match results.

**LLM role:** parser and normalizer only. It converts unstructured text (catalog files, scraped pages, RFP documents) into structured JSON that matches the DB schema. It never decides match quality.

**Matching role:** pure code. Compares structured requirement attributes against structured product attributes using typed operators defined per product class.

---

## 2. Data Model

### Classification Layer

```sql
product_class (
  id, name, auto_created BOOL, created_at
)

attribute_def (
  id, class_id → product_class,
  name,                              -- key used in attributes JSONB
  label,                             -- human-readable
  datatype  TEXT CHECK IN ('numeric','text','bool','enum'),
  match_op  TEXT CHECK IN ('eq','gte','lte'),
  canonical_unit TEXT,               -- e.g. 'V', 'A', 'mm' — null for non-numeric
  allowed_values TEXT[]              -- for enum type only
)
```

`attribute_def` rows are created once per class — either from pre-seeded data or auto-generated by the LLM when a new class is encountered during ingest. After creation they are reused for all future ingests and RFP extractions.

### Supplier (renamed from `company`)

```sql
supplier (
  id, name NOT NULL,
  official_website,
  contact_email, contact_phone,
  country, description,
  categories TEXT[],                 -- e.g. ['electrical','lab']
  scrape_status, last_scraped_at
)
```
All fields except `name` are optional.

### Catalog Side

```sql
product (
  id, supplier_id → supplier,
  class_id → product_class,
  name, mpn,                         -- model/part number
  attributes JSONB,                  -- {key: canonical_value} matching attribute_def.name
  source TEXT CHECK IN ('upload','scrape'),
  is_stale BOOL DEFAULT false,
  created_at, updated_at
)

product_price (
  product_id PK → product,
  price NUMERIC, currency TEXT DEFAULT 'JOD',
  as_of DATE, source_file TEXT
)                                    -- structurally separate; never enters LLM context

product_price_history (
  id, product_id → product,
  price NUMERIC, currency TEXT,
  recorded_at
)

catalog_ingest (
  id, supplier_id → supplier,
  kind TEXT CHECK IN ('company_upload','admin_upload','scrape'),
  filename, status, error_msg,
  started_at, finished_at
)
```

### Tender Side

```sql
tender (
  id, user_id,
  filename, file_type,
  status TEXT CHECK IN ('uploading','extracting','matching','done','failed'),
  created_at
)

tender_supplier (
  tender_id → tender,
  supplier_id → supplier,
  PRIMARY KEY (tender_id, supplier_id)
)

tender_line (
  id, tender_id → tender,
  line_no, raw_text,
  description, qty NUMERIC, qty_unit TEXT,
  class_id → product_class,          -- null if class unknown
  attributes JSONB,                  -- normalized requirements, same keys as attribute_def
  status TEXT CHECK IN ('extracted','matched','partial','not_found','unclassified')
)

match_result (
  id,
  line_id → tender_line UNIQUE,
  product_id → product,              -- best match (null if not_found)
  match_type TEXT CHECK IN ('exact','spec'),
  score INT,                         -- 0–100
  attribute_verdicts JSONB,          -- [{attr, required, offered, verdict}]
  status TEXT CHECK IN ('matched','partial','not_found'),
  alternatives JSONB                 -- [{product_id, score, attribute_verdicts}] top-5 ≥40
)
```

### Auth

```sql
app_user (
  id, username UNIQUE NOT NULL,
  password_hash NOT NULL,
  role TEXT CHECK IN ('USER','ADMIN')
)
```
Replaces the current in-memory map in `AuthController`.

## 3. LLM Tasks

The LLM is called in exactly three situations. All calls use `temperature=0`, enforce JSON output via structured output mode, and are cached by `sha256(systemPrompt|userMessage)`.

### Task 1 — Parse catalog data

Called per batch of raw text from an uploaded file or scraped page.

**System prompt includes:** known `product_class` names and their `attribute_def` keys/units, so output is consistent with existing classes.

**Output per product:**
```json
{
  "class_name": "Multimeter",
  "name": "Fluke 179",
  "mpn": "FLUKE-179",
  "price": 320.00,
  "currency": "JOD",
  "attributes": {
    "max_voltage": 1000,
    "max_voltage_unit": "V",
    "display_type": "digital",
    "has_trms": true
  }
}
```

### Task 2 — Define a new product class

Called only when `class_name` from Task 1 is not found in `product_class`. Runs once per new class; result is persisted and reused.

**Input:** a sample of 3–5 products belonging to the new class.

**Output:**
```json
{
  "class_name": "Multimeter",
  "attribute_defs": [
    {"name": "max_voltage",  "datatype": "numeric", "match_op": "gte", "canonical_unit": "V"},
    {"name": "display_type", "datatype": "enum",    "match_op": "eq",  "allowed_values": ["digital","analog"]},
    {"name": "has_trms",     "datatype": "bool",    "match_op": "eq",  "canonical_unit": null}
  ]
}
```

### Task 3 — Parse RFP/tender lines

Called once per uploaded RFP document.

**System prompt includes:** all known `product_class` names + `attribute_def` keys, so the LLM outputs attribute keys consistent with the catalog side.

**Output per line:**
```json
{
  "class_name": "Multimeter",
  "description": "True RMS digital multimeter, 1000V",
  "qty": 5,
  "qty_unit": "pcs",
  "attributes": {
    "max_voltage": 1000,
    "max_voltage_unit": "V",
    "has_trms": true
  }
}
```

## 4. Catalog Ingestion Pipeline

Three entry points feed the same pipeline:

| Entry point | Who | Endpoint |
|---|---|---|
| Company catalog upload | Company or admin | `POST /suppliers/{id}/catalog/upload` |
| Scrape trigger | Admin or system | `POST /suppliers/{id}/catalog/scrape` |
| Auto-scrape | System (on RFP supplier selection) | Internal trigger |

**Pipeline steps (same for all three):**

```
1. Create catalog_ingest row (status=RUNNING)

2. Extract raw text
   - Upload → DocumentParsingService (PDF/DOCX/XLSX → text)
   - Scrape  → ScrapeService + Playwright (supplier's official_website)

3. LLM Task 1 → [{class_name, name, mpn, price, attributes}]

4. For each parsed product:
   a. Resolve class_name → product_class (case-insensitive match on name)
   b. Class not found → LLM Task 2 → create product_class + attribute_def rows
   c. Normalize attribute values to canonical units (code, via unit_conversion table)
   d. Upsert product on (supplier_id, mpn) or (supplier_id, LOWER(name)):
      - Exists → update attributes + is_stale=false
                 price changed → write product_price_history, update product_price
      - New    → insert product + product_price

5. Products not seen in this run → is_stale=true

6. Update catalog_ingest → status=DONE / FAILED
```

**What is kept from existing code:** `DocumentParsingService`, `ScrapeService` (Playwright), `ShedLock` daily refresh job, `@Async` job pattern.

## 5. RFP Processing Pipeline

```
1. POST /rfp/upload (file + supplier_ids[])
   → create tender (status=extracting)
   → create tender_supplier rows

2. DocumentParsingService → raw text

3. LLM Task 3 (system prompt includes all known classes + attribute_defs)
   → [{class_name, description, qty, qty_unit, attributes}]

4. For each extracted line:
   a. Resolve class_name → product_class
   b. Unknown class → save tender_line with class_id=null, status=unclassified
   c. Normalize attribute values to canonical units
   d. Save tender_line

5. Update tender → status=matching
   Trigger async matching job

6. Matching engine runs (Section 6)
   → saves match_result per tender_line

7. Update tender → status=done / failed
```

Frontend polls `GET /jobs/{id}` unchanged (existing `JobStatusPoller`).

**Auto-scrape rule:** before step 6, for each selected supplier with zero products, trigger scrape (timeout: 5 minutes). If scrape completes in time, proceed to matching with the new catalog. If it times out, matching runs without that supplier's products — those lines will surface as `not_found` with a `no_catalog` note.

## 6. Matching Engine

Runs as an `@Async` job per tender. For each `tender_line`:

### Stage 1 — Exact match
```sql
SELECT * FROM product
WHERE supplier_id IN (SELECT supplier_id FROM tender_supplier WHERE tender_id = :tid)
  AND is_stale = false
  AND (LOWER(name) = LOWER(:description) OR LOWER(mpn) = LOWER(:description))
LIMIT 1
```
Hit → `match_type=exact`, `score=100`, `status=matched`. Skip Stage 2.

### Stage 2 — Spec-level match

**2a. Scope to class:**
```sql
SELECT * FROM product
WHERE supplier_id IN (...)
  AND class_id = :line_class_id
  AND is_stale = false
```

**2b. Score each candidate:**

Load `attribute_def` rows for the class. For each required attribute in `tender_line.attributes`:

| match_op | comparison (all values in canonical units) |
|---|---|
| `eq` | `product.attributes[key] == line.attributes[key]` |
| `gte` | `product.attributes[key] >= line.attributes[key]` |
| `lte` | `product.attributes[key] <= line.attributes[key]` |

Per attribute verdict: `COMPLIANT` / `DEVIATION` / `UNVERIFIABLE` (attribute missing from product)

```
score = (COMPLIANT count / total required attributes) × 100
```

**2c. Select results:**
- **Best match** — highest score candidate (score > 0)
- **Alternatives** — all other candidates with score ≥ 40, ordered by score desc, max 5

**2d. Status thresholds:**
- `score = 100` → `matched`
- `score 40–99` → `partial`
- `score < 40` or no candidates → `not_found`

**2e. Save `match_result`** with `attribute_verdicts` + `alternatives JSONB`.

## 8. What Changes vs. Current Code

| Current | Change |
|---|---|
| `company` table | Renamed to `supplier`, extra optional fields added |
| `instrument` table | Replaced by `product` + `product_price` |
| `required_instrument` | Replaced by `tender_line` |
| `rfp_request` | Renamed to `tender` |
| `LlmService.scoreMatch()` | Deleted — matching is now pure code |
| `AuthController` in-memory users | Replaced by `app_user` table + `UserRepository` |
| Keyword LIKE search | Replaced by two-stage exact + spec matching |
| `ScrapeService.persistScrapedInstruments()` | Replaced by unified catalog ingest pipeline |

**Kept as-is:** `DocumentParsingService`, `ScrapeService` (Playwright crawl), `@Async`/`ShedLock` job infrastructure, `JwtFilter`/`JwtUtil`, frontend upload + polling flow, Flyway migration setup, Docker Compose.

---

## 9. Migration Strategy

- New Flyway migrations (`V3+`) add the new schema alongside existing tables
- Existing data in `company`/`instrument` can be migrated or dropped (no production data yet)
- Old tables dropped in a later migration once new pipeline is confirmed working
